bestool alertd · CHK-RSC

Reporting Schema Rollout QA

alertd reads the version stamped on a server's reporting schema, grades it against what canopy offers for the version that server runs, and applies the offered one when they differ. Applying is the check's self-heal, so it happens on its own, in the daemon, with no operator action. These flows are the ones a test suite cannot stand in for.

Record results on the Linear card as 🤖 ✅ TEST_n comments. The done boxes here only keep your place.

Before you start

Access and arrangement

Every flow below needs all of these. Gather them first: TEST_1 stalls for a full sweep interval if you discover a missing piece halfway through.

  • A test server running the daemon, Linux or Windows, registered to canopy, with a Tamanu central on it. Not a deployment carrying real patient data.
  • Its exact Tamanu version, as canopy knows it. bestool tamanu doctor --check version -a reports it, and the artifact must be registered against that exact string. A range pattern is refused for a reporting schema.
  • Its canopy group id, and a second group that the test server is not in. Without the second group the scoping half of TEST_1 asserts nothing.
  • A canopy admin device credential, or a device with an enabled declaration building that group's artifacts. Both registrations in TEST_1 go through it.
  • A database shell on the server's Tamanu central, to read the schema comment directly.
  • The daemon's log. The apply reports itself only there.
Server · Linux · daemon log
journalctl -u bestool-alertd -f
Server · Windows · daemon log
Get-Service bestool-alertd
Get-Content -Wait (Get-ChildItem 'C:\ProgramData\bestool\logs' |
  Sort-Object LastWriteTime -Descending | Select-Object -First 1).FullName

Timings that decide how long you wait

WhatValueWhy it matters here
Sweep interval60sHow often the check runs and can trigger an apply.
Offer cache5 minThe server reuses canopy's last answer, so a fresh registration takes up to this long to be seen.
Heal floor5 minMinimum between two apply attempts, applied after a success as well.
Backoff ceiling1 hourWhere attempts keep failing.
Lock timeout30sHow long the apply waits for a report query to release the schema.
Statement timeout5 minPer statement inside the apply.
Whole-apply deadline10 minAfter this the attempt is abandoned and reported failed.

Worst case from registering an artifact to seeing the apply is around ten minutes. Anything longer is worth reporting.

Phase 1 · Whatever autodeploys

Smoke

Twenty minutes. If any of these three is wrong, stop: the flows below will fail for reasons that have nothing to do with them.

SMOKE_1

The check is registered and runs

Server · Linux and Windows
bestool tamanu doctor --check tamanu-central:reporting_schema -a

Passes when a reporting_schema line appears in the output with a result on it. A missing line means the check was not registered for this server's applications, which is the whole feature absent.

Watch for

  • The bare name may be refused with needs the subject it reports for, listing the subjects. That is the CLI asking you to qualify it, so use whichever subject it names for this server.
SMOKE_2

With nothing published, the check stands down

Run SMOKE_1's command before registering anything.

Passes when the result is a skip reading none offered for this version. Canopy owes a build, and that is canopy's finding rather than this server's, so a failure here would raise the same alert on every server in the fleet.

Watch for

  • A skip reading canopy unreachable instead. That is a connectivity problem, and TEST_1 cannot run until it is fixed.
  • A warning reading could not ask canopy what is offered. Canopy answered with a refusal, usually 401 or 403, which means this server's credential is not being accepted.
SMOKE_3

The stamp reaches canopy

Apply Fixture A by hand on the server's database, then wait one sweep and open the server in canopy.

Server · database shell · reads the stamp back
SELECT obj_description(oid, 'pg_namespace') AS stamp
FROM pg_namespace WHERE nspname = 'reporting';

Passes when canopy shows reportingSchemaVersion for this server carrying the version you stamped. That fact is what the fleet view reads to say which schema each server is on. To read it on the server instead, bestool tamanu doctor --check tamanu-central:reporting_schema --json carries it under wire.applications.<app>.detail, beside tamanuVersion.

Watch for

  • Only the version is published, never the digest. A stamp of 2.60.0 sha256-… shows as 2.60.0, and that is correct.
  • No fact at all means the comment did not parse as a version. The comment is arbitrary text, so anything unparseable, blank, or over 128 characters reads as no stamp and is deliberately dropped rather than published.

Phase 2 · A registered server and a real canopy

Flows

TEST_1

A server takes the schema canopy offers and applies it unattended

Nothing automated builds a canopy client against a real canopy, presents a device certificate, or runs the daemon's sweep-then-heal loop. The unit tests grade in process against a hand-built offer. Group scoping is only real once a second group exists to be excluded.

Setup

  1. Note the server's exact Tamanu version and its group id.
  2. Read and write down the current stamp using SMOKE_3's query. It may be empty.
  3. Take Fixture A and Fixture B below, replacing 2.60.0 in each with the server's exact version.

Steps

  1. Register Fixture B against the other group first, so a wrong answer cannot be mistaken for a timing artefact.
  2. Register Fixture A against the server's own group.
  3. Leave the daemon alone and watch its log. Do not run doctor --fresh.
  4. When applied reporting schema appears, read the stamp back and read the marker view.
  5. Run bestool tamanu doctor --check reporting_schema -a and confirm it now passes.
Any machine with the credential · register for a group
curl --cert device.pem --key device.key \
  -X POST \
  -H 'Content-Type: application/sql' \
  --data-binary @fixture-a.sql \
  https://<canopy>/artifacts/groups/<group-id>/2.60.0/reporting-schema/any
Server · database shell · which fixture landed
SELECT obj_description(oid, 'pg_namespace') AS stamp
FROM pg_namespace WHERE nspname = 'reporting';

SELECT marker FROM reporting.qa_marker;

Passes when the marker reads QA_FIXTURE_A, the stamp carries the version followed by a sha256- digest the server appended itself, and the check reports a pass. The digest is the point: it is how two builds of one version are told apart, and it is written by alertd rather than by the schema's own SQL.

Watch for

  • doctor --fresh never applies anything. An on-demand sweep is deliberately free of side effects; only the daemon's own periodic tick heals. Running it and seeing nothing change tells you nothing, and it is the easiest way to spend an hour concluding the feature is broken.
  • A marker of QA_FIXTURE_B is a real defect and worth stopping for: the server took another group's schema.
  • Nothing happening for up to ten minutes is expected. The offer cache and the heal floor are five minutes each.
  • The log line the offered reporting schema has already been applied without stamping its version means an earlier attempt applied something that did not stamp as expected, and that artifact is now refused for the life of the process. Restart the daemon to clear it.
  • If this ships with the check still registered against every Tamanu application rather than centrals only, a facility server in the same group will apply the schema too. That is a known open defect on the card, so record it against that rather than filing it fresh.
TEST_2

An apply that runs while reports are being read

The schema is dropped and recreated whole, so an apply and a running report want the same objects. A test database has no concurrent readers and never meets this.

Setup

  1. Finish TEST_1, so the server has a schema applied by the daemon.
  2. Register Fixture A again with one view's text changed, so canopy holds a different digest for the same version and the check grades a newer build as offered.

Steps

  1. In a database shell, open a transaction that reads a reporting view and holds it open for longer than the lock timeout.
  2. Wait for the daemon to attempt the apply.
  3. Read the stamp while the transaction is still open.
  4. Close the transaction, wait for the next attempt, and read the stamp again.
Server · database shell · hold the schema
BEGIN;
SELECT count(*) FROM reporting.qa_marker;
SELECT pg_sleep(60);
COMMIT;

Passes when the held attempt logs applying the reporting schema failed naming a lock timeout, the stamp is unchanged while the transaction is open, and the schema is still readable throughout. After the transaction closes, a later attempt applies and the stamp moves to the new digest.

Watch for

  • A failed attempt is the correct outcome here, not a defect. The apply gives up rather than waiting behind a report, and the check stays red until the next attempt succeeds. Report it only if the schema is left missing or half-built.
  • Reports should keep working for the whole flow. A window where a report errors saying a reporting view does not exist is worth reporting with the timestamp.
  • Repeated failures stretch to an hour apart. If you are waiting a long time for the successful attempt, that is the backoff rather than a stall.

Ship with the flows

Fixtures

Two small schemas, each carrying a marker view so you can tell at a glance which one a server took. Replace 2.60.0 with the server's exact Tamanu version in both. They are deliberately tiny: a real build is around 128 views, and none of them would tell you anything a marker does not.

Fixture A · the group's own schema

Save as fixture-a.sql. Validated against a real Tamanu central: two views, the grant lands, and the stamp reads back.

fixture-a.sql
drop schema if exists reporting cascade;
create schema reporting;
comment on schema reporting is '2.60.0';
grant usage on schema reporting to tamanu_reporting;
alter default privileges in schema reporting grant select on tables to tamanu_reporting;
create or replace view "reporting"."qa_marker" as (select 'QA_FIXTURE_A'::text as marker);
create or replace view "reporting"."patient_count" as (select count(*) as patients from patients);

Fixture B · the other group's schema

Save as fixture-b.sql. Identical except for the marker, so the only thing it can prove is that scoping held.

fixture-b.sql
drop schema if exists reporting cascade;
create schema reporting;
comment on schema reporting is '2.60.0';
grant usage on schema reporting to tamanu_reporting;
alter default privileges in schema reporting grant select on tables to tamanu_reporting;
create or replace view "reporting"."qa_marker" as (select 'QA_FIXTURE_B'::text as marker);
create or replace view "reporting"."patient_count" as (select count(*) as patients from patients);

Constraints worth knowing before you improvise

  • Register with application/sql, text/plain or application/octet-stream. Canopy serves back whatever content type the registration named, and the server refuses anything else rather than running it as SQL.
  • 32MB ceiling on both sides. An artifact over it is refused at registration.
  • A fixture must carry no BEGIN, COMMIT or ROLLBACK. The whole schema goes to the server as one batch, which is what makes a failure partway leave the old schema in place. Transaction control inside the artifact ends that batch early, and a later failure then leaves the server with an empty reporting schema and no stamp.
  • The role tamanu_reporting has to exist. Tamanu creates it at startup from 2.60, so a server that has run once has it.

Grading and stamp parsing are covered by the suite. What is not: the canopy round trip with a real credential, group scoping against a second group, and the apply under load. Those three are why this page exists.
